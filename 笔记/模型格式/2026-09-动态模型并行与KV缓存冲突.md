> 来源：追问"模型并行能不能替换使用——层1 的 A 跑完，层2 可以调 A 也可以调 B，输出哪张卡有空就进哪张，那 KV 缓存怎么记"。一句话：**计算可以无状态地动态路由，但 KV 缓存是有状态的，它把"请求—层—卡"三者绑在一起；动态模型并行的难点不在算力调度，而在如何低成本地维护和迁移这份状态。**

### 一、先把设想翻译成并行术语

> 设想："层1 的 A 跑完，调层2 的 A 也可以调层2 的 B，然后输出哪张层3 卡有空就进去。"

| 设想中的描述 | 对应概念 |
| :--- | :--- |
| 层2 有 A、B 两份 | 层/专家的**多副本** |
| 层1 输出可以进 A 或 B | **动态路由 / 负载均衡** |
| 层3 哪张卡有空就进 | **在线调度（scheduling）** |

**直觉是对的**：模型并行不一定非要"层1 永远在卡0、层2 永远在卡1"这种静态绑定，可以做成动态、按负载调度的。工业界已有对应实践：

| 系统/概念 | 做法 |
| :--- | :--- |
| **MoE（Mixture of Experts）** | 每个 token 路由到不同专家（层内多副本） |
| **DeepSeek / Switch Transformer** | 专家分布在多卡，token 动态分发 |
| **Orca / vLLM continuous batching** | 请求动态进出不同计算单元 |
| **Serverless 推理** | 层作为独立服务，按空闲度调度 |

### 二、核心矛盾：KV 缓存

#### 1. KV 缓存是什么

自回归生成每生成一个新 token，注意力需要用到**之前所有 token 的 K、V**；为不重复计算就存下来，这就是 KV Cache。

```
第 t 步生成时：
  当前 token 的 Q × [历史所有 K] → 注意力权重
                  [历史所有 V] → 加权求和
  历史 K、V 就是 KV Cache，不用重算
```

形状大致：`[num_layers, batch, num_heads, seq_len, head_dim]`

> **关键：KV Cache 是"按层"存的，而且和"哪个请求、哪段历史"强绑定。**

#### 2. 动态调度与 KV 缓存的冲突

假设层1 在卡0 算完，请求 R 的 KV 存在**卡0 的层1缓存**里。现在层2 要动态选卡：

- 若层2 选到**卡1 的副本 A** → 卡1 没算过 R 的层2，**没有这份 KV**，要么重算、要么从卡0 传过来；
- 若选到**卡1 的副本 B**（另一份拷贝）→ 同样没有 R 的层2 KV；
- 而**下一步生成**时层2 又可能被调度到另一张卡，那份 KV 又得跟着搬。

> **KV 缓存和"计算它的那张卡、那个模型副本"是绑定的。动态换卡 = 缓存要么跟着搬，要么重建。**

### 三、工业界的五种解法

| 方案 | 做法 | 优点 | 缺点 / 适用 |
| :--- | :--- | :--- | :--- |
| **① KV 跟着请求走（迁移）** | 请求被调度到哪张卡，就把它的 KV 一起搬过去 | 调度自由 | KV 很大（长上下文每层几 MB~几十 MB），**跨卡带宽是瓶颈**（NVLink 尚可，PCIe 很慢）；适用于 PD 分离 |
| **② 请求亲和性调度（Affinity）** | 同一请求的所有层**尽量固定在同一组卡**上，调度器记录"R 的 KV 在卡0/1/2"，后续优先调度到这几张卡；只有全忙时才迁移 | 避免 KV 迁移 | **目前 LLM serving 的主流做法**：KV 亲和性 > 纯负载均衡 |
| **③ 副本间共享 KV** | 副本 A/B 要处理同一请求 R 时**共享同一份 KV**（共享显存池或 RDMA 访问） | 省复制 | 有同步开销（DeepSpeed-Inference、部分 MoE 实现这么做） |
| **④ 无状态化，每步重算** | 不存 KV，每步重算整个序列的 K/V | 无缓存管理 | 计算量 O(n²) 爆炸，只适合极短序列或训练 |
| **⑤ 层为调度单位 + KV 按请求分片** | Prefill 全部层在卡组上算完生成完整 KV；Decode 时各层在各自卡上维护自己那段 KV，**请求固定绑定这条流水线**；动态调度只发生在**请求进入时** | 兼顾流水线与局部性 | 进入后不再换卡 |

**vLLM 的 PagedAttention** 是把方案①做到极致：KV 按 block 管理，可以像操作系统分页一样在卡间搬运、共享。

### 四、核心答案

1. **KV 缓存按"层 + 请求 + 历史 token"存**，天然绑定在"算过这个请求这一层"的那张卡上。
2. **若允许层2 在副本 A/B 间动态切换，就必须解决**：副本 B 没有请求 R 的层2 KV → 要么**迁移**、要么**重算**、要么**共享**；下一步再切到别的卡，KV 又要动。
3. **真实系统的做法**：
   - **调度以请求为单位，而不是以层为单位**——请求一旦进入某条并行流水线就**固定绑定**，KV 留在原地，不随层乱跳；
   - 动态负载均衡只发生在**请求级别**（新请求选空闲流水线），而不是**层级别**（层2 随机选卡）；
   - 若一定要层级动态，就用 **PagedAttention 式 KV 分页 + 迁移**，代价是通信。
4. **换句话说**："层2 的 A 或 B 随便调"在**计算上**可行，但**状态（KV）**让这件事变贵——因为 KV 不是无状态的，它记得"我之前在哪张卡上算过"。工程上通常**牺牲一点调度自由度，换取 KV 的局部性（locality）**。

### 五、一句核心总结

> **计算可以无状态地动态路由，但 KV 缓存是有状态的，它把"请求—层—卡"三者绑在一起。动态模型并行的难点不在算力调度，而在如何低成本地维护和迁移这份状态。主流方案是"请求级亲和调度 + KV 分页迁移"，而不是层级的随机换卡。**

**可继续展开的方向**：PagedAttention 怎么管理 KV、MoE 怎么做专家路由、PD 分离怎么传 KV。
