### 一、PyTorch 执行一行代码的完整步骤（远超 5 步）

以 `x = torch.matmul(A, B)` 为例：

| 步骤 | 做什么 | 谁在做 | 耗时占比 |
| :--- | :--- | :--- | :--- |
| ① 解析 Python 代码 | 解释器读取这行，理解"要调用 matmul" | Python 解释器 | 小 |
| ② 参数类型检查 | 检查 A/B 是否 Tensor、形状、dtype | PyTorch Python 层 | 小 |
| ③ 算子派发（Dispatch） | 按输入类型(CPU/GPU、dtype)选底层实现(几十种分支) | PyTorch C++ 层 | 中 |
| ④ 张量元数据检查 | 查 shape（能否相乘）、stride 是否连续 | PyTorch C++ 层 | 小 |
| ⑤ 内存分配 | 为输出 C 分配显存 | CUDA 驱动 | 中 |
| ⑥ 数据搬运 H2D | A/B 在 CPU 则拷到 GPU | PCIe | **很大** |
| ⑦ 启动 GPU Kernel | 把编译好的 CUDA 代码推进命令队列 | CUDA 驱动 | 小 |
| ⑧ GPU 执行计算 | SM 真正算矩阵乘法 | GPU | **很大** |
| ⑨ CPU-GPU 同步 | 调 `.item()`/`.cpu()` 时 CPU 被迫等 GPU | CPU 等待 | 可能很大 |
| ⑩ 数据搬运 D2H | 结果拷回 CPU | PCIe | 可能很大 |
| ⑪ 返回 Python 对象 | 封装成 Tensor 返回 | Python/C++ | 小 |
| ⑫ 形状推导 + Autograd 构图 | 构建计算图记录操作供反向传播用（训练时尤其耗时；推理用 `no_grad()` 关掉） | 框架层 | 训练时大 |

### 二、"同步 / 查形状"到底指什么

| 操作 | 具体在做什么 | 为什么慢 |
| :--- | :--- | :--- |
| **查形状** | 每个算子执行前检查输入维度/大小/内存布局；matmul 要求最后两维能乘 | 单次快，几百个算子累积 + Python/C++ 频繁切换后不可忽视 |
| **同步** | CPU 发指令给 GPU 默认异步，但下一步若要用上一步结果，CPU 被迫等 GPU 完成 | 同步时 CPU 空转干等，过多同步严重拖慢 |

**类比**：你是餐厅经理(CPU)，厨师是 GPU。你每接一单写好菜单(发 kernel)递给厨师，本可继续接下一单；但若非要"亲眼看到这盘菜装盘"再写下一单，就一直站着干等，后面的单子全堵住——这就是同步的代价。

### 三、`torch.compile` 做了什么

核心思路：**把 Python 写的"零散指令"编译成一个优化的"整体计划"**。

| 优化手段 | 在做什么 | 效果 |
| :--- | :--- | :--- |
| 算子融合 | 连续小算子（matmul+add+relu）合并成一个 GPU Kernel | 3 个 kernel → 1 个，大幅减少启动开销 |
| 消除中间张量 | `y=A+B; z=y*C` 融合成 `(A+B)*C`，不分配 y | 省显存和读写带宽 |
| 减少 Python/C++ 边界 | 整个图编译成高效 C++ 程序，Python 只调一次 | 大幅减少"发号施令"的 CPU 开销 |
| 静态形状推导 | 编译期已知所有形状，运行期不再反复查 | 省掉"查形状"步骤 |
| 内核自动调优 | 按 GPU 型号/矩阵大小选最优 CUDA kernel（cuBLAS 或 Triton） | 让计算更快 |

**用法**：`compiled_fn = torch.compile(fn)`，之后多次调用走编译版。

### 四、`CUDA Graph` 做了什么

思路：**把一系列 GPU 操作录制成"录像"，一键重放**。

| 模式 | 每个迭代做的事 | 开销 |
| :--- | :--- | :--- |
| 普通 Eager | 发指令→同步→发指令→同步……重复 N 次 | 每次走完整"发号施令"流程 |
| CUDA Graph | **录制一次**：录下所有 kernel 启动指令；**回放 N 次**：一键启动全部 kernel，CPU 不介入 | CPU 几乎不参与 |

核心收益：消除 CPU-GPU 同步、消除 kernel 启动开销、录制时预分配中间张量显存（回放不再反复分配/释放）。

局限：**输入形状必须固定**；有 if/else 动态分支无法录制；第一次要先录制（预热必需）。

```python
g = torch.cuda.CUDAGraph()
static_in  = torch.randn(1024, 1024, device='cuda')
static_w   = torch.randn(1024, 1024, device='cuda')
with torch.cuda.graph(g):            # 录制一次
    static_out = torch.matmul(static_in, static_w)
for i in range(1000):
    static_in.copy_(new_input)       # 拷进预留显存
    g.replay()                       # 回放整个图
    result = static_out
```

### 五、对比与结合使用

| 维度 | torch.compile | CUDA Graph |
| :--- | :--- | :--- |
| 优化层面 | 算子融合、形状推导、代码生成 | kernel 启动调度、内存分配优化 |
| 适用范围 | 任意动态形状/模型结构 | 静态形状、无动态分支的固定图 |
| 预热 | 首次编译较慢 | 需先录制一次 |
| 后续速度 | 非常快（融合后 kernel） | 极快（几乎零 CPU 开销） |
| 能否一起用 | ✅ 可！`mode="reduce-overhead"` 内部自动启用 CUDA Graph | — |

```python
compiled_model = torch.compile(model, mode="reduce-overhead")
```

| 技术 | 核心目的 | 类比 |
| :--- | :--- | :--- |
| Eager（默认） | 逐行执行，灵活但慢 | 每做一个菜都现切现炒 |
| torch.compile | 小操作融合成大操作，减少"发指令" | 先写完整菜谱让厨师批量做 |
| CUDA Graph | 整批操作录成宏命令一键重放 | 整个宴席录成视频，直接播放不再指挥 |

> 做批量/重复推理时强烈建议加 `torch.compile`；输入形状固定再配合 `mode="reduce-overhead"`，提升非常明显。

### 六、TensorRT 模型运行时到底靠什么技术

TensorRT 不是 CUDA Graph（Graph 只是其可选"加速插件"），核心是一个**面向特定 GPU、高度优化的机器码程序**。

1. **一段编译好的 GPU 代码**：优化器把整个模型当整体，编译成一系列直接跑在 GPU 上的 CUDA Kernel。
2. **轻量运行时（Runtime）**：不做"逐行解释"，只负责调度执行已编译好的完整 GPU 代码序列。
3. **CPU 角色大幅简化**：只需向命令队列发一次"开始执行这个预编译程序"的指令，GPU 自己一个 kernel 接一个地跑，无需 CPU 不断介入。

| 核心技术 | 作用 | 为什么高效 |
| :--- | :--- | :--- |
| 静态图编译 | 推理时结构固定，一次性把整个图编译布局好 | 省掉 PyTorch 运行时反复建图/优化的动态开销 |
| 内核融合 + 自动调优 | 融合连续小算子成"超级内核"，并在你的 GPU 上测几百种实现选最快 | 减少启动次数，最大化并行利用率 |
| 显存复用/池化 | 编译期看全模型生命周期，给中间特征图安排固定地址 | 避免反复申请/释放，降碎片 |
| 低精度推理 | FP32 → FP16 / INT8 | 数据减半/1/4，省带宽、提速、省显存 |
| CUDA Graph 支持 | 捕获整个静态 GPU 程序执行过程录成"宏" | 高频重复请求时彻底消灭 CPU 调度开销 |

**一句话**：TensorRT 是"基于静态编译的推理优化技术"——静态图编译 + 内核融合生成最贴近硬件极限的 GPU 程序，配合显存复用、低精度，可选叠加 CUDA Graph 打包执行。它跑在**自己生成的一套专属于当前模型和 GPU 硬件的本地代码**上，而不是跑在类似解释器的通用框架上。

**记忆对比**：PyTorch Eager = 每点一个菜都跟厨师交代做法；TensorRT = 直接交一份翻译成机器语言的完整菜谱，厨师自己按部就班完成所有菜品。
