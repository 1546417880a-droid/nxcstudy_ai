ROS 三种通信机制怎么选：Topic · Service · Action

同一个 ROS 图里三种机制可以混用 —— 区别不在"新不新"，而在数据是"一直流"、"问一次"还是"跑很久"。
图 2 / 2 · 通信机制
01

Topic 发布 / 订阅Publish–Subscribe

类比：广播电台 —— 只管往外播，谁在听、几个在听都不关心
  • 异步、一对多（也可多对多），发布者与订阅者互不知道对方存在，靠话题名解耦
  • 适合持续变化的状态和高频数据流，丢一帧通常无所谓
  • 用 QoS 调可靠性：传感器 best_effort，控制指令 reliable
  • 没有"完成"的概念，节点活着就一直流
典型/scan/vehicle/speed/cmd_vel
02

Service 请求 / 响应Request–Response

类比：打电话查话费 —— 问一次，答一次，然后挂断
  • 同步阻塞：客户端发出 Request 后等 Response，超时即失败
  • 严格一对一，服务端先注册服务名，客户端按名字调用
  • 中间没有进度反馈，只有"成功 / 失败 + 结果"，不适合几十秒以上的任务
  • 适合"查一次""算一次""触发一次"的瞬时操作
典型/get_battery_level夹爪开合单帧红灯检测
03

Action 动作Goal · Feedback · Result

类比：点外卖 —— 下单后能看到进度，也能中途取消
  • 面向长任务：Goal 下发 → 持续 Feedback → 最终 Result
  • 执行中可随时 Cancel，这是 Service 做不到的
  • 底层是拼出来的：Goal / Cancel / Result 走 Service，Feedback / Status 走 Topic
  • 适合"几分钟起步 + 用户盯着进度 + 可能中途改主意"的任务
典型NavigateToPose机械臂抓取自动泊车
怎么选
数据一直在变→ Topic传感器、车辆状态、控制指令流
问一次答一次→ Service查询、触发、单次计算
跑很久、要进度、可能反悔→ Action导航、抓取、泊车、探索建图
Action 不是第四套底层协议：Goal / Cancel / Result 走 Service，Feedback / Status 走 Topic —— "能看进度 + 能取消"是拼出来的能力，不是新的传输方式。
