## 视觉 SLAM 前端"三步走"总结（特征提取/匹配/三角化+外参）(2026.09)

> 来源：梳理视觉 SLAM / VO 最核心的前端流程。一句话：**图像 → 提特征 → 匹配点对 → 三角化出点云 + 解出相机外参**。这是整个 SLAM 持续运行的骨架。

### 一、三步走总览

```
图像A + 图像B
   ↓ ① 提取 ORB 特征
  A → 特征点A + 描述子A；B → 特征点B + 描述子B
   ↓ ② 特征匹配
  描述子A vs 描述子B → 距离最小的点对 → 2D-2D 匹配点对
   ↓ ③ 用匹配点对做两件事
  ├── ① 三角化 → 生成 3D 点云
  └── ② 计算相机运动 → 得到 B 相对 A 的相机外参
```

### 二、两种处理路径（取决于深度是否已知）

| 相机类型 | 顺序 | 工具 |
|---|---|---|
| **单目**（无深度） | 先求**外参** → 再**三角化**点云 | 对极几何 → 三角测量 |
| **双目 / RGB-D**（有深度） | 先求**点云** → 再求**外参** | 视差/深度图 → PnP |

- **单目注意**：初始化时求出的平移是**尺度不确定**的（归一化平移）——只知道相对比例，不知道真实米数。
- **PnP**（Perspective-n-Point）：用 3D 点云 + 其在下一幅图的 2D 像素坐标，直接解位姿。

### 三、外参到底指什么

- 外参 = **旋转矩阵 R + 平移向量 t**。
- 表示：**第二幅图拍摄时，相机坐标系相对于第一幅图（世界系原点）的位置和朝向**——即 **B 相对 A 的位姿变换**。你理解的"以第一个相机坐标系为基准"准确。

### 四、系统持续运行模式

```
【第1帧】初始化，建立初始地图
【第2帧】提特征 → 与第1帧匹配 → 计算外参（跟踪）+ 三角化新点入图
【第3帧】提特征 → 与第2帧匹配（或与地图匹配）→ 计算外参 + 三角化新点
   ... 循环
```

> 后续的局部优化、回环检测、全局优化，都是在这个骨架上构建的。

## PyTorch 执行原理 + torch.compile + CUDA Graph + TensorRT 运行时 (2026.09)

> 来源：梳理"PyTorch 执行一行代码要做什么、同步/查形状指什么、torch.compile 和 CUDA Graph 优化了什么、TensorRT 模型运行时到底靠什么技术"的完整问答。

### 一、PyTorch 执行一行代码的完整步骤（远超 5 步）

以 `x = torch.matmul(A, B)` 为例：

| 步骤 | 做什么 | 谁在做 | 耗时占比 |
| :--- | :--- | :--- | :--- |
| ① 解析 Python 代码 | 解释器读取这行，理解"要调用 matmul" | Python 解释器 | 小 |
| ② 参数类型检查 | 检查 A/B 是否 Tensor、形状、dtype | PyTorch Python 层 | 小 |
| ③ 算子派发（Dispatch） | 按输入类型(CPU/GPU、dtype)选底层实现(几十种分支) | PyTorch C++ 层 | 中 |
| ④ 张量元数据检查 | 查 shape（能否相乘）、stride 是否连续 | PyTorch C++ 层 | 小 |
| ⑤ 内存分配 | 为输出 C 分配显存 | CUDA 驱动 | 中 |
| ⑥ 数据搬运 H2D | A/B 在 CPU 则拷到 GPU | PCIe | **很大** |
| ⑦ 启动 GPU Kernel | 把编译好的 CUDA 代码推进命令队列 | CUDA 驱动 | 小 |
| ⑧ GPU 执行计算 | SM 真正算矩阵乘法 | GPU | **很大** |
| ⑨ CPU-GPU 同步 | 调 `.item()`/`.cpu()` 时 CPU 被迫等 GPU | CPU 等待 | 可能很大 |
| ⑩ 数据搬运 D2H | 结果拷回 CPU | PCIe | 可能很大 |
| ⑪ 返回 Python 对象 | 封装成 Tensor 返回 | Python/C++ | 小 |
| ⑫ 形状推导 + Autograd 构图 | 构建计算图记录操作供反向传播用（训练时尤其耗时；推理用 `no_grad()` 关掉） | 框架层 | 训练时大 |

### 二、"同步 / 查形状"到底指什么

| 操作 | 具体在做什么 | 为什么慢 |
| :--- | :--- | :--- |
| **查形状** | 每个算子执行前检查输入维度/大小/内存布局；matmul 要求最后两维能乘 | 单次快，几百个算子累积 + Python/C++ 频繁切换后不可忽视 |
| **同步** | CPU 发指令给 GPU 默认异步，但下一步若要用上一步结果，CPU 被迫等 GPU 完成 | 同步时 CPU 空转干等，过多同步严重拖慢 |

**类比**：你是餐厅经理(CPU)，厨师是 GPU。你每接一单写好菜单(发 kernel)递给厨师，本可继续接下一单；但若非要"亲眼看到这盘菜装盘"再写下一单，就一直站着干等，后面的单子全堵住——这就是同步的代价。

### 三、`torch.compile` 做了什么

核心思路：**把 Python 写的"零散指令"编译成一个优化的"整体计划"**。

| 优化手段 | 在做什么 | 效果 |
| :--- | :--- | :--- |
| 算子融合 | 连续小算子（matmul+add+relu）合并成一个 GPU Kernel | 3 个 kernel → 1 个，大幅减少启动开销 |
| 消除中间张量 | `y=A+B; z=y*C` 融合成 `(A+B)*C`，不分配 y | 省显存和读写带宽 |
| 减少 Python/C++ 边界 | 整个图编译成高效 C++ 程序，Python 只调一次 | 大幅减少"发号施令"的 CPU 开销 |
| 静态形状推导 | 编译期已知所有形状，运行期不再反复查 | 省掉"查形状"步骤 |
| 内核自动调优 | 按 GPU 型号/矩阵大小选最优 CUDA kernel（cuBLAS 或 Triton） | 让计算更快 |

**用法**：`compiled_fn = torch.compile(fn)`，之后多次调用走编译版。

### 四、`CUDA Graph` 做了什么

思路：**把一系列 GPU 操作录制成"录像"，一键重放**。

| 模式 | 每个迭代做的事 | 开销 |
| :--- | :--- | :--- |
| 普通 Eager | 发指令→同步→发指令→同步……重复 N 次 | 每次走完整"发号施令"流程 |
| CUDA Graph | **录制一次**：录下所有 kernel 启动指令；**回放 N 次**：一键启动全部 kernel，CPU 不介入 | CPU 几乎不参与 |

核心收益：消除 CPU-GPU 同步、消除 kernel 启动开销、录制时预分配中间张量显存（回放不再反复分配/释放）。

局限：**输入形状必须固定**；有 if/else 动态分支无法录制；第一次要先录制（预热必需）。

```python
g = torch.cuda.CUDAGraph()
static_in  = torch.randn(1024, 1024, device='cuda')
static_w   = torch.randn(1024, 1024, device='cuda')
with torch.cuda.graph(g):            # 录制一次
    static_out = torch.matmul(static_in, static_w)
for i in range(1000):
    static_in.copy_(new_input)       # 拷进预留显存
    g.replay()                       # 回放整个图
    result = static_out
```

### 五、对比与结合使用

| 维度 | torch.compile | CUDA Graph |
| :--- | :--- | :--- |
| 优化层面 | 算子融合、形状推导、代码生成 | kernel 启动调度、内存分配优化 |
| 适用范围 | 任意动态形状/模型结构 | 静态形状、无动态分支的固定图 |
| 预热 | 首次编译较慢 | 需先录制一次 |
| 后续速度 | 非常快（融合后 kernel） | 极快（几乎零 CPU 开销） |
| 能否一起用 | ✅ 可！`mode="reduce-overhead"` 内部自动启用 CUDA Graph | — |

```python
compiled_model = torch.compile(model, mode="reduce-overhead")
```

| 技术 | 核心目的 | 类比 |
| :--- | :--- | :--- |
| Eager（默认） | 逐行执行，灵活但慢 | 每做一个菜都现切现炒 |
| torch.compile | 小操作融合成大操作，减少"发指令" | 先写完整菜谱让厨师批量做 |
| CUDA Graph | 整批操作录成宏命令一键重放 | 整个宴席录成视频，直接播放不再指挥 |

> 做批量/重复推理时强烈建议加 `torch.compile`；输入形状固定再配合 `mode="reduce-overhead"`，提升非常明显。

### 六、TensorRT 模型运行时到底靠什么技术

TensorRT 不是 CUDA Graph（Graph 只是其可选"加速插件"），核心是一个**面向特定 GPU、高度优化的机器码程序**。

1. **一段编译好的 GPU 代码**：优化器把整个模型当整体，编译成一系列直接跑在 GPU 上的 CUDA Kernel。
2. **轻量运行时（Runtime）**：不做"逐行解释"，只负责调度执行已编译好的完整 GPU 代码序列。
3. **CPU 角色大幅简化**：只需向命令队列发一次"开始执行这个预编译程序"的指令，GPU 自己一个 kernel 接一个地跑，无需 CPU 不断介入。

| 核心技术 | 作用 | 为什么高效 |
| :--- | :--- | :--- |
| 静态图编译 | 推理时结构固定，一次性把整个图编译布局好 | 省掉 PyTorch 运行时反复建图/优化的动态开销 |
| 内核融合 + 自动调优 | 融合连续小算子成"超级内核"，并在你的 GPU 上测几百种实现选最快 | 减少启动次数，最大化并行利用率 |
| 显存复用/池化 | 编译期看全模型生命周期，给中间特征图安排固定地址 | 避免反复申请/释放，降碎片 |
| 低精度推理 | FP32 → FP16 / INT8 | 数据减半/1/4，省带宽、提速、省显存 |
| CUDA Graph 支持 | 捕获整个静态 GPU 程序执行过程录成"宏" | 高频重复请求时彻底消灭 CPU 调度开销 |

**一句话**：TensorRT 是"基于静态编译的推理优化技术"——静态图编译 + 内核融合生成最贴近硬件极限的 GPU 程序，配合显存复用、低精度，可选叠加 CUDA Graph 打包执行。它跑在**自己生成的一套专属于当前模型和 GPU 硬件的本地代码**上，而不是跑在类似解释器的通用框架上。

**记忆对比**：PyTorch Eager = 每点一个菜都跟厨师交代做法；TensorRT = 直接交一份翻译成机器语言的完整菜谱，厨师自己按部就班完成所有菜品。

## 视频流式推理的帧角色元数据 `_build_streaming_frame_metadata`（KV 缓存"选择性入缓存"）(2026.09)

> 来源：梳理推理侧一个记录每帧"缓存身份"的元数据函数。一句话：**它不是每个 token/帧都进 KV 缓存，而是按角色选择性入缓存**，只为应对视频高帧率、高计算成本做的优化。它记录的角色 = 帧在缓存策略中的身份（scale 帧 / keyframe / 普通帧），供可视化、评估、调试时核对。

### 一、核心结论：与文本 Transformer KV 缓存同构，但多一个"角色"开关

| 步骤 | 文本 Transformer（标准自回归） | 视频流式推理（用此元数据） |
| :--- | :--- | :--- |
| 当前 token/帧生成 Q | ✅ | ✅ |
| Q 去 attend 历史 KV | ✅（**所有**历史 token） | ✅（**仅 scale + 所有 keyframe**） |
| 融合 V 得到输出 | ✅ | ✅ |
| 当前 token/帧的 KV 是否入缓存 | ✅ 是（**全部**都进） | ❌ **仅当角色 = 0 或 1** |

- **关键区别不在 attention，而在"写回缓存"这一步**：普通帧的 Q 照常去 attend 全部缓存 KV，只是它自己的 KV 不被写入缓存（用完即弃）；文本模型是每个 token 的 KV 都回写。
- 帧率越高（如 30fps）、帧间冗余越大，越不需要每帧都当参考——全存 KV 显存会爆。

### 二、三个角色（帧的缓存身份）

| 角色码 | 含义 | 是否入缓存 | 类比（文本 Transformer） |
| :--- | :--- | :--- | :--- |
| `0` = **scale 帧** | 全局坐标底图，后续每一帧都要 attend | ✅ **必须存** | 相当于"系统提示词 / 初始上下文" |
| `1` = **keyframe** | 长期参考点，相当于关键摘要帧 | ✅ **存** | 相当于被长期保留的历史 token |
| `2` = **非关键帧** | 只 attend 现有缓存，用完即弃（"只看不记"） | ❌ **不存** | 相当于临时 token |

### 三、缓存规模控制公式

```
缓存中 KV ≈ 总帧数 / keyframe_interval + scale_frames
```

- 用 `keyframe_interval`（关键帧间隔）+ scale 帧数控制缓存大小，**远小于原始总帧数 S**。
- 帧序 / 角色分配是**逐帧判断**的，该元数据就是把这套逐帧判断的结果事后记录成"身份标签"。

### 四、元数据记录下来的作用

- **可视化**：只画关键帧；
- **评估**：确认哪些帧被当作全局底座（scale 帧）；
- **调试**：核对帧序、角色分配是否与 phase-2 逐帧判断一致。

## Transformer 自回归推理的 KV 缓存机制（纯语言版）(2026.09)

> 来源：梳理"自回归每层 KV 缓存到底存的是什么"。一句话：**每层的 KV 缓存存的是该层为每个历史 token 算出来的"原始 K/V 投影向量"，不是聚合后的上下文结果 h_l**。

### 一、单层内部流程（第 l 层，当前 token t）

```
输入 h_{l-1}^{(t)}（第1层即 token embedding）
  1. Q_l = W_Q_l·h_{l-1}；K_l = W_K_l·h_{l-1}；V_l = W_V_l·h_{l-1}
  2. ★ K_l、V_l 立刻写入第 l 层的 KV 缓存（供未来 token 用）★
  3. 取缓存全部历史 K/V：K_cache=[K_l^{(1..t-1)}]，V_cache=[...]
  4. attention 输出 = softmax(Q_l · K_cacheᵀ) · V_cache   ← 聚合上下文
  5. 过 MLP + 残差 + LayerNorm → 输出 h_l^{(t)}（传给 l+1 层）
```

### 二、为什么存"原始投影"，不存"聚合后的"

| 问题 | 答案 |
| :--- | :--- |
| KV 缓存存什么？ | **原始投影向量** K_l / V_l（当前 token 刚算出的） |
| 聚合后的 attention 输出存哪？ | **不存**，作为本层输出 h_l 往下传，用完即过 |
| 为何不能存聚合值？ | 未来 token 需要**自己重新算与每个历史 token 的相似度权重**；存聚合值 = 权重已被别人平均，逐 token 信息丢失 |
| 为何不直接复用 h_l（已含上下文）？ | 每层处**不同特征空间**，要在该层自己的语义空间里重新算 attention 分布；l+1 层不复用 l 层的 attention 结果 |

### 三、多层数据流与生成（推理）阶段

- **每层各有一份独立缓存**：Token 走过 L 层，每层各算一次 K_l/V_l 并写入**自己的**第 l 层缓存。
- **自回归生成第 T+1 个 token 时**：只对当前 token 算 Q_l，再对它 attend 各层缓存的全部历史 K/V → h_L 进 LM Head。
- **纯解码（推理）阶段不再写入新 K/V**；写入发生在**训练 / 预填充（prefill）**阶段，供后续 token 使用。

### 四、为什么必须同时存 K 和 V

- **K（Key）**：和 Q 点积 → 注意力权重（"跟谁相关"）
- **V（Value）**：加权求和 → 聚合内容（"取到什么信息"）
- 缺一不可：只有 V 无 K = 不知权重怎么分；只有 K 无 V = 有权重没内容可加权。

### 五、一句核心总结

> **每层 KV 缓存 = 该层为每个历史 token 算出的原始 K/V 投影向量**，目的是让未来 token 在该层特征空间里能自由重新分配注意力权重；每层输出 h_l 是聚合结果，只作下一层输入，**不进缓存**。

## 量化核心公式 + 反量化格式 + scale 保存 + 按需反量化 (2026.09)

> 来源：梳理"量化公式精简、反量化到 float16 与 float32 的区别、int8 模型为什么要存 scale、是不是整层提前反量化"的完整问答。一句话：**量化 = 用 256 个整数档位近似权重范围；int8 是"编号"，scale 是"每个编号代表多少"，两者缺一不可，且逐层按需反量化才省显存。**

### 一、核心思想与最简公式

**整数档位对应权重的上下限范围，权重再对应到某个整数上。**

```
1. 算 scale
   scale = (max - min) / 255
   （对称量化：scale = max_abs / 127）

2. 量化
   int8 = round(w / scale) + zero_point
   clamp(int8, -128, 127)

3. 反量化
   w' = (int8 - zero_point) × scale
```

**只记两行：**

```
int8 = round(w / scale)      # 权重 → 整数
w'   = int8 × scale          # 整数 → 权重（还原）
```

**本质：把连续的权重，按 `scale` 等距切成 256 份，每份用一个整数编号。**

```
权重范围 [min, max]
   │
   ├─ 切成 256 份，每份 = scale = (max-min)/255
   ├─ 每个权重 w → 最近的档位编号 = round(w/scale)
   └─ 存储这个整数编号（int8）
```

### 二、反量化输出：float16 vs float32

**反量化公式完全相同** `w' = (int8 - zero_point) × scale`，区别只在**结果存成什么格式**。

| 维度 | float16 | float32 |
| :--- | :--- | :--- |
| 总位数 | 16 bit（2 字节） | 32 bit（4 字节） |
| 有效十进制位 | ~3~4 位 | ~7 位 |
| 数值范围 | ±65504 | ±3.4×10³⁸ |
| 存储/带宽 | 省一半 | 费一倍 |
| 计算速度 | 快（Tensor Core 支持） | 慢 |
| 表示 int8 值够不够 | ✅ 够（int8 只有 ~2~3 位） | ✅ 过剩 |

**两种误差必须分清：**

| 误差来源 | 大小 | 能否避免 |
| :--- | :--- | :--- |
| **int8 量化误差** | 大（~scale/2） | ❌ 量化时已丢 |
| **float16 表示误差** | 小（~1e-3） | ✅ 用 float32 可避免 |

> **float16 vs float32 的差异，比 int8 量化误差小几个数量级，通常可忽略。**

**实际选择（混合精度）：**

| 场景 | 选择 | 原因 |
| :--- | :--- | :--- |
| 矩阵乘（Tensor Core） | **float16** | 快、省显存 |
| 累加（accumulation） | **float32** | 避免长序列累加误差 |
| 数值敏感层 | **float32** | 保证稳定 |
| 推理部署 | **float16** | 速度优先 |

```
int8 权重 → 反量化到 float16 → 矩阵乘
                ↓
          累加用 float32
                ↓
          结果转回 float16
```

**类比**：int8 量化 = 把照片压成 256 色（信息已丢）。反量化到 float16 = 普通显示器看，够清楚；float32 = 专业显示器看，更精细——但照片本身只有 256 色，看不出更多。**显示器再好，也变不出照片里没有的颜色。**

### 三、为什么必须保存 scale（+ zero_point）

int8 存储的是"档位编号"，本身没有物理意义：

```
int8 = 32   ← 代表 0.5024？还是 0.0032？还是 5.024？
w' = (32 - zero_point) × scale

若 scale = 0.0157 → w' = 0.5024
若 scale = 0.001  → w' = 0.032
```

**同一个 int8 = 32，scale 不同，还原出的权重完全不同。scale 是"解码密钥"。**

| 保存内容 | 作用 | 大小 |
| :--- | :--- | :--- |
| **int8 权重** | 档位编号 | 1 字节/权重 |
| **scale** | 解码密钥（每层/每通道一个） | 4 字节 × 层数（或通道数） |
| **zero_point** | 零点偏移（非对称量化需要） | 1 字节 × 层数 |
| 元信息 | 量化方案（per-tensor/per-channel） | 少量 |

| 方案 | scale 数量 | 说明 |
| :--- | :--- | :--- |
| per-tensor | 每层 1 个 | 整层共用一个 |
| per-channel | 每输出通道 1 个 | 每个通道各自一个 |
| per-group | 每组 1 个 | 每 128 个权重一个 |

**scale 开销可忽略**：某层权重 4096×4096 ≈ 1600 万：

```
int8 权重：1600 万字节 ≈ 16 MB
per-channel scale：4096 个 float ≈ 16 KB   （占比 < 0.1%）
per-tensor scale：1 个 float ≈ 4 字节       （更可忽略）
```

**类比**：int8 像"地图上的坐标编号"，scale 像"比例尺"——没有比例尺，坐标"32"不知道代表 32 米还是 32 公里。**编号 + 比例尺，才能还原真实位置。**

### 四、按需反量化（省显存的关键）

**是"计算到这一层才反量化这一层"，不是提前把整层权重全反量化。**

```
推理到第 L 层
   ↓
只把第 L 层的 int8 权重，按需反量化
   ↓
算完第 L 层，反量化的临时结果丢弃
   ↓
到第 L+1 层，再按需反量化
```

| 层面 | 省在哪 |
| :--- | :--- |
| **模型存储** | 权重始终是 int8（1 字节），不存 float（4 字节）→ 省 4 倍 |
| **计算时** | 只反量化当前层、当前块，算完丢弃 → 峰值显存不膨胀 |

**错误做法（提前全反量化）**：int8 权重 → 全部反量化 → float32 权重膨胀 4 倍，**省显存的意义没了**。

**正确做法（按需反量化）**：显存始终是 int8；计算第 L 层时只反量化第 L 层，临时 float 用完即弃；峰值 = int8 权重 + 少量临时 float。

### 五、一句核心总结

> **量化 = 用 256 个整数档位去近似权重范围。scale = 范围/255（每档代表多少），int8 = round(w/scale)（权重落在哪档），反量化 = int8 × scale（档位还原成权重）。**
>
> **int8 模型 = int8 权重 + scale（+ zero_point）**：int8 是"编号"，scale 是"每个编号代表多少"，缺一不可；scale 开销极小但不可或缺。
>
> **反量化到 float16 还是 float32 公式相同**，差异远小于 int8 量化本身误差；实际用"反量化到 float16 + 累加用 float32"的混合精度。
>
> **显存里始终是 int8，float 只在该层计算时临时存在、用完丢弃——逐层按需反量化，才是省显存的关键。**

## 针孔相机：为什么像素数 = fx × (H/Z)——h 是 F 的 H/Z 倍 (2026.09)

> 来源：梳理内参 fx = F / pixel_size 的来龙去脉。一句话：**像高 h 和焦距 F 在同一张成像平面上，h 就是 F 按相似三角形比例 H/Z 缩放出来的，所以 h 是 F 的 H/Z 倍；把 h 换算成像素数时 F 又被 pixel_size 除掉，于是得到 fx × (H/Z)。**

### 一、物理量先对齐（所有量都在"成像平面"上） 
「像素坐标系 → 成像平面物理坐标 → 相机坐标系 → 世界坐标系」

| 符号 | 含义 | 量纲 |
| :--- | :--- | :--- |
| **H** | 物体的真实高度 | 米 / mm（世界系） |
| **Z** | 物体到相机的距离（深度） | 米 / mm（世界系） |
| **F** | 焦距（光心到成像平面的距离） | mm（**成像平面上**） |
| **h** | 物体在成像平面上成的**像高** | mm（**成像平面上**） |
| **pixel_size** | 单个像素的物理尺寸 | mm / 像素（**成像平面上**） |
| **fx** | 内参 = F / pixel_size | 像素（量纲被除掉了） |

关键：**F 和 h 是同一条线段上的两个长度**（都在成像平面这个物理平面上），所以它们之间可以直接比。

### 二、相似三角形 → h 是 F 的 H/Z 倍

```
        物体                         成像平面
        ┌──┐ H                     ┌─┐ h
        │  │                       │ │
        └──┘                       └─┘
         ╲                         ╱
          ╲                       ╱
           ╲                     ╱
            ╲___________________╱
                  光心 O
              ├──── Z ────┤  ├─ F ─┤
```

由相似三角形（三角形 O-物体 vs 三角形 O-像）：

```
h / F = H / Z

→  h = F × (H / Z)
```

**这就是"h 相对于 F 的比例"这句话的意思**：h 和 F 在同一张成像平面上，h = F 乘以一个纯比例因子 (H/Z)。**h 是 F 的 H/Z 倍。**

### 三、从物理像高 h 换算到像素数

相机传感器把物理长度切成一个个像素，所以：

```
像素数 = h / pixel_size
       = [ F × (H/Z) ] / pixel_size
       = (F / pixel_size) × (H/Z)
       = fx × (H/Z)
```

### 四、为什么 h 能用 fx 来表示（核心一句）

> **h 和 F 在同一张成像平面上，h 是 F 的 H/Z 倍；所以"把 F 除以 pixel_size 得到 fx"这件事，等价于"把 h 除以 pixel_size 得到像素数"——两者被同一个 scale 变换（÷pixel_size）作用了一次，比例关系不变。**

推广到 2D（u、v 两个方向独立各除一次）：

```
u = fx × (X / Z) + cx
v = fy × (Y / Z) + cy
其中 fx = F / pixel_size_x，fy = F / pixel_size_y（通常相等）
```

### 五、一句话记忆 + 常见误区

**记忆**：`h/F = H/Z`（相似三角形）→ `h = F·H/Z`（像高）→ `pixels = h/pixel_size = fx·H/Z`（像素数）。**全程只有一个比例 H/Z，fx 只是把"毫米"翻译成"像素"的汇率。**

| 误区 | 纠正 |
| :--- | :--- |
| 以为 fx 是"焦距的像素表示"，所以有三个焦距 | 只有**一个**物理焦距 F。"fx / fy"只是水平/垂直方向像素尺寸不同导致的两次单位换算 |
| 以为公式是 F·H/Z 直接得像素数 | **量纲不对**：F·H/Z 是**毫米**（物理像高 h），必须再 ÷ pixel_size 才得到像素 |
| 以为 Z 变大像变小是因为 fx 变了 | fx 是**内参、出厂固定**；像变小是因为比例因子 H/Z 变小 |
| 以为"h 是 F 的 H/Z 倍"是近似 | 针孔模型下这是**精确**的相似三角形关系 |

## 检测任务头不只是"一个 conv"：三层共享/分流结构（FCOS3D 为例）(2026.09)

> 来源：纠正"backbone 特征已共享，任务头是不是就只是一个 conv"的混淆。一句话：**任务头不一定只是 1×1 conv，FCOS3D 的任务头是"共享卷积塔 + 各任务独立子塔 + 1×1 conv 线性读出"的小型子网络；backbone/FPN 的共享与任务头内部的共享是**两个不同层次**的事。**

### 一、先分清两种"共享"（这是混淆的根源）

```
图像
  → Backbone + FPN          ← 第一层共享（所有任务共享）
  → 共享特征 f (256维)
  → ┌─────────────────────────────────┐
    │  任务头内部                      │
    │  ├─ 共享卷积塔（shared_convs）    │ ← 第二层共享（所有任务头共享）
    │  │   Conv3×3 → GN → ReLU         │
    │  │   Conv3×3 → GN → ReLU         │
    │  │                               │
    │  └─ 各任务独立子塔                 │ ← 第三层分流（每个任务独立）
    │      ├─ cls 子塔 → 1×1 conv      │
    │      ├─ reg 子塔 → 1×1 conv      │
    │      └─ ...                      │
    └─────────────────────────────────┘
```

| 层次 | 是否共享 | 作用 |
| :--- | :--- | :--- |
| Backbone + FPN | 所有任务共享 | 通用视觉特征 |
| **共享卷积塔** | 所有任务头共享 | 任务相关的通用变换 |
| **各任务独立子塔** | 每个任务独立 | 任务专用特征转换（= 任务子空间转换） |
| 最后 1×1 conv | 每个输出值独立 | 线性读出 |

### 二、任务头内部的"特征转换"是什么

以 FCOS3D 的 `FCOSMono3DHead` 为例（简化）：

```python
# 共享卷积塔（所有任务共享）
shared_convs = [
    Conv2d(256, 256, 3, padding=1), GN(256), ReLU(),
    Conv2d(256, 256, 3, padding=1), GN(256), ReLU(),
]

# 各任务独立子塔
cls_convs = [Conv2d(256, 256, 3), GN, ReLU, ...]   # 分类专用
reg_convs = [Conv2d(256, 256, 3), GN, ReLU, ...]   # 回归专用

# 最后线性读出
cls_score = Conv2d(256, 10, 1)   # 分类输出
bbox_pred = Conv2d(256, 9, 1)    # 回归输出
```

所以任务头不是"一个 conv"，而是：

```
共享卷积塔（2层 Conv+GN+ReLU）
  → 任务独立子塔（2层 Conv+GN+ReLU）
    → 1×1 conv 线性读出
```

### 三、为什么任务头里还要做特征转换

因为 **backbone/FPN 的特征是"通用"的，不是"任务专用"的**：

- Backbone 学的是"图像里有什么边缘、纹理、物体"；
- 但分类需要"语义判别特征"，回归需要"几何定位特征"——这两类特征**不一样**；
- 所以任务头内部要再做一次**任务专用转换**：把共享特征投影到任务关心的子空间。

### 四、三种任务头设计对比（按"共享到哪一层"分）

| 设计 | 结构 | 参数量 | **表达能力** | 任务冲突 | 任务专用特征转换 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **A** 纯线性读出 | `f → 1×1 conv → 输出` | 最少 | **最弱**（只能线性投影，学不出新特征） | 无（各任务独立投影） | ❌ 无 |
| **B** 共享塔 + 读出 | `f → 共享 Conv+ReLU → 1×1 conv` | 中等 | **中等**（能提非线性特征，但任务间共用同一套变换） | 严重（共享变换被多任务拉扯） | ❌ 无（只有共享转换） |
| **C** 共享塔 + 独立子塔 + 读出（FCOS3D） | `f → 共享塔 → 各任务独立子塔 → 1×1 conv` | 最多 | **最强**（先学通用变换，再各自提任务特征） | 缓解（先共享再分流，冲突在子塔处解开） | ✅ 有 |

**表达能力从 A → C 递增的本质**：

- A：只能对**已有特征**做线性组合，无法造出新的、更抽象的特征；
- B：共享塔能造新特征，但所有任务**被迫用同一套**，表达能力被"一鱼多吃"限制；
- C：每个任务都能在共享表示之上**再造一层自己的非线性特征**，等于给每个任务配了独立的小网络——表达能力最强，也因此参数最多。

### 五、完整图景与一句话总结

```
图像
  → Backbone + FPN          ← 共享：通用视觉特征
  → 共享特征 f (256维)
  → 共享卷积塔               ← 共享：任务相关的通用变换
  → 任务相关特征 (256维)
  ├─ cls 独立子塔 → 分类专用特征 → 1×1 conv → 分类输出
  ├─ reg 独立子塔 → 回归专用特征 → 1×1 conv → 回归输出
  └─ ...
```

> **任务头不只是单个 conv**：FCOS3D 的任务头 = 共享卷积塔 + 各任务独立子塔 + 1×1 conv 线性读出。共享塔做"任务相关的通用转换"，独立子塔做"任务专用特征转换"（即任务子空间转换），最后线性读出。**Backbone/FPN 的共享** 与 **任务头内部的共享/分流** 是两个不同层次的事。

## 任务子空间：本质是"换基"而不是"降维"（同维子空间也是子空间）(2026.09)

> 来源：追问"独立子塔输出的特征维度和输入一样（都 256），那还能叫投影到任务子空间吗"。一句话：**子空间的本质是方向（基）的选择，不是维度的降低；同维子空间也是子空间，满秩线性变换换一组基，就是在做子空间投影。**

### 一、数学上：子空间不等于低维空间

n 维空间 V 的子空间 W 可以是：

- **低维的**：256 维里的一条线（1 维）、一个平面（2 维）；
- **同维的**：256 维里，由 256 个"不是原来那组基"的新方向张成的另一个 256 维空间。

在 3 维空间里随便找三个线性无关的向量，它们张成的还是整个 3 维空间，但这三个向量定义了一组**新的基**，相当于换了个"视角"。**"子空间"这个词的重点是方向，不是维度。**

### 二、独立子塔做的是"线性变换"，不是"降维"

```
cls_feat = W_cls · f + b_cls      # W_cls: 256×256
reg_feat = W_reg · f + b_reg      # W_reg: 256×256
```

输出维度和输入一样时，W 是 256×256 的矩阵。它一般**满秩**，所以不丢信息，但它做了一件事：**把 f 重新组合成一组新的方向。**

- 原来 f 的 256 维，是 **backbone 学出来的基**；
- 经过 W_cls 后，cls_feat 的 256 维，是**分类任务自己学出来的基**。

两组基张成的都是 256 维，但**方向不一样**。分类真正关心的那些方向，在 cls_feat 这组基下可能只集中在少数几个维度上；在原 f 下可能分散在很多维度里。

> **"投影到分类子空间"不一定意味着降维，而是意味着"换一组对分类更友好的基"。**

### 三、直观类比：RGB → 任务方向

假设一张 RGB 照片，三个通道 R/G/B：

- 分类可能只关心"是不是红色物体"，真正需要的是"**红色程度**"这个方向；
- 回归可能只关心"物体边缘在哪"，真正需要的是"**亮度梯度**"这个方向。

```
cls_feat = W_cls · [R, G, B]     # W_cls 是 3×3 满秩
reg_feat = W_reg · [R, G, B]     # W_reg 是 3×3 满秩
```

维度都是 3 维，没降维。但 cls_feat 的第 1 维可能强烈对应"红色程度"、后两维是噪声；reg_feat 的第 1 维强烈对应"亮度梯度"。**它们真正关心的子空间其实只有 1 维**，只是被埋在一个 3 维输出里。

### 四、为什么不直接降维，非要保持同维

| 原因 | 说明 |
| :--- | :--- |
| ① 兼容后续 1×1 读出 | 读出层通常期望输入 256 维（输出才是类别数/坐标数），子塔降维太狠会限制读出层表达 |
| ② 训练更稳定 | 满秩线性 + 非线性优化比强行降维更平滑，不易出现信息瓶颈 |
| ③ 让网络自己决定用多少维 | 保持 256 维，训练让有用信息集中到少数维度、其余接近零/噪声——**软性子空间选择**，比硬降维更灵活 |
| ④ 残差连接常见 | 子塔常用 `x + conv(x)`，输入输出维度必须一致才能相加 |

### 五、硬投影 vs 软投影

| 方式 | 结构 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **软子空间投影**（常见） | 子塔保持同维（256→256），训练后信息集中在少数维度 | 不强制丢信息、灵活、训练稳 | 参数多、结构上没显式约束 |
| **硬子空间投影** | `W: 256 → 64` 直接降维 | 参数少、计算省、任务冲突更小（各自只留自己的 64 维） | 可能丢信息，64 维不够时性能掉 |

实际中很多设计**子塔内部保持维度，最后读出时才降维**；也有轻量设计直接在子塔里降维，看具体权衡。

### 六、一句核心总结

> **子空间 ≠ 低维空间；同维线性变换 = 换基 = 一种子空间投影。** 独立子塔输出 256 维，不代表没做子空间投影——它做的是满秩线性变换，把通用特征重组成对分类/回归更友好的方向。真正被"选择"的子空间可能只是这 256 维里的少数几个方向，但结构上保留 256 维，**让网络自己决定用哪些方向**。

## 车体坐标系与三类变换：外参 / 动态位姿 / 全局校正（2026.09）

> 来源：梳理"外参固定和位姿每帧变为什么不矛盾、检测物体该放哪个系、odom 系原点为什么在 t=0"的完整问答。一句话：**四个坐标系串成三条性质完全不同的变换链——①传感器→车体（静态标定）②车体→odom（动态位姿，IMU 测旋转 + 轮速测平移）③odom→map（全局校正，GNSS/地图匹配）；几乎所有坐标系事故都是把这三个里的某两个搞混了。**

### 〇、全部坐标系与变换

```
┌─────────┐     ┌─────────┐
│  相机系  │     │  雷达系  │
└────┬────┘     └────┬────┘
     │ T_cb          │ T_lb      ← ①静态外参：标定一次，永久有效
     └───────┬───────┘
             ▼
      ┌─────────────┐
      │   车体系 B   │             ← 通常直接定在 IMU 上（省一次标定）
      └──────┬──────┘
             │ T_{odom←B}(t)       ← ②动态位姿：每帧变，IMU+轮速算，GNSS/激光修正
             ▼
      ┌─────────────┐
      │   odom 系    │             ← = t=0 那一刻的车体系，之后永远不动
      └──────┬──────┘
             │ T_{map←odom}        ← ③全局校正：低频、慢漂、偶尔跳
             ▼
      ┌─────────────┐
      │    map 系    │             ← ENU / 经纬度，和 HD 地图、GNSS 对齐
      └─────────────┘
```

| # | 变换 | 含义 | 变不变 | 谁提供 | 频率 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ① | `T_{b←c}`、`T_{b←l}` | 相机/雷达挂到车体 | **固定** | 离线标定 | —— |
| ② | `T_{odom←b}(t)` | 自车在世界里的位姿 | **每帧变** | IMU + 轮速（+修正） | 100 Hz+ |
| ③ | `T_{map←odom}` | 局部系按到真实世界 | 慢漂 + 偶尔跳 | GNSS-RTK / 地图匹配 | 1–10 Hz |

> ①③ 最容易混为一谈——它们都是"固定/缓慢"的，但一个是**传感器几何**、一个是**全局对齐**，混了会写出"车一动外参就变"这种逻辑。

### 一、"外参固定"和"位姿每帧变"为什么不矛盾

- **外参** = 两个坐标系之间的相对变换，是**商**：`T_{c←l} = T_{w←c}⁻¹ · T_{w←l}`
- **位姿** = 某坐标系相对世界系的**绝对**变换。

相机和雷达刚性固连在同一台车上，车一动，两者的世界位姿同时被同一个增量 ΔT 左乘：

```
(ΔT·T_wc)⁻¹ · (ΔT·T_wl)
= T_wc⁻¹ · ΔT⁻¹ · ΔT · T_wl
= T_wc⁻¹ · T_wl          ← ΔT 被夹在中间消掉，结果不变
```

**相对量对共同的刚体运动免疫。** 这才是"外参固定"的本质——不是螺丝拧得紧，而是它在数学上就不可能变。正确说法：

> 不是"相机每帧有新外参"，而是**相机每帧有新的世界位姿**；外参是相机位姿和雷达位姿的商，两者同步变化，**商恒定**。

推论：雷达不需要自己跑一遍 SLAM，它的世界位姿**寄生在车体位姿**上：`T_{w←l} = T_{w←b} · T_{b←l}`。整台车只需估一条轨迹，所有传感器共享。

### 二、不会写错的记法：下标相消

一切变换写成 `T_{目标←源}`，合成就是内下标抵消，跟分数约分一样：

```
T_{世界←雷达} = T_{世界←车体} · T_{车体←雷达}
                     ↑ 内下标 b 抵消
```

**方向约定是这类代码里九成的 bug 来源**：你写的 `T_lc` 到底是"l 到 c"还是"c 到 l"？SLAM 库输出的是 `T_wc`（camera→world，直接可用）还是 `T_cw`（world→camera，SLAM 主流约定，需求逆）——看到 (R, t) 第一件事是确认方向。

工程上用 4×4 齐次矩阵：

```
T = [ R  t ]        P_w = T_{w←b}(t) · T_{b←l} · [P_l; 1]
    [ 0  1 ]
```

链式合成自动成立，求逆有闭式解 `Rᵀ, -Rᵀt`。

### 三、动态位姿（②）从哪来

**先分岔：绝对定位 vs 自车运动**（很多人一上来就分错）

| | 绝对定位 Localization | 自车运动 Odometry |
| :--- | :--- | :--- |
| 回答 | 我在哪里 | 我动了多少 |
| 参考系 | 世界/地图系 | 上一时刻的自己 |
| 典型源 | RTK-GNSS、地图匹配 | IMU、轮速、激光/视觉里程计 |
| 漂移 | 不漂 | 会漂、累积 |
| 频率 | 低，1–20 Hz | 高，100–1000 Hz |
| 会失锁 | 会（隧道、峡谷） | 不会 |

> **传感器融合要的是右边那一列。GNSS 只是左边的修正项，不是主源。**

各传感器分工：

| 传感器 | 测什么 | 频率 | 强项 | 弱项 |
| :--- | :--- | :--- | :--- | :--- |
| IMU | 角速度 + 加速度 | 100–200 Hz | 高频、不依赖外界、旋转极准 | 平移极烂 |
| 轮速计 | 车轮转速 | 50–100 Hz | 直接测速、无积分漂移、便宜 | 打滑失效、只有纵向 |
| 方向盘转角 | 前轮角 → 横摆角速度 | 低 | 便宜 | 精度低、要标转向比 |
| GNSS-RTK | 绝对位置 | 5–10 Hz | 绝对、不漂 | 频率低、会跳、会失锁 |
| 激光里程计 | 点云配准 (ICP/GICP/NDT) | 10 Hz | 相对运动最准 | 特征少时退化、算力大 |
| 视觉里程计 | 特征跟踪 + 三角化 | 20–30 Hz | 便宜 | 单目尺度不确定、怕光照 |

#### 核心配方：IMU 给旋转，轮速给平移

两个数量级对比：

```
陀螺零偏 ~1 °/h     → 积分 60 秒，姿态误差 ≈ 0.02°   ✅ 短期极其可靠
加计零偏 ~0.01 m/s² → 积分 60 秒，位移误差 ≈ 18 m    ❌ 完全不能用
                        （误差 ∝ t²：10 秒就 0.5 m）
```

**加速度计不能用来求位移**——双重积分下误差随 t² 爆炸。所以：

```
ΔR（旋转增量） ← IMU 陀螺仪积分    准
Δt（平移增量） ← 轮速计积分        准
加速度计只用来做重力对齐/倾斜估计，不用于求位移
```

这就是**航位推算（dead reckoning）**，车载里程计的地基。GNSS 和激光里程计在它之上做低频修正，整体是**预测-更新**结构：

```
预测：IMU 预积分推一步（100–200 Hz，保证高频连续）
更新：GNSS-RTK / 轮速 / 激光 / 视觉 来了就修正一次（1–10 Hz）
```

#### 汽车独有的免费午餐：非完整性约束（NHC）

轮子不能横着走，所以车体系下瞬时速度只有一个分量：

```
v_y ≈ 0    （不能侧滑）
v_z ≈ 0    （不能跳）
```

白送两个速度约束，把 3D 位姿估计直接**降成 1D**（只有纵向速度 + 横摆角速度）。这是车载里程计比无人机、机器人稳得多的根本原因——**物理结构替你简化了问题**。

- **副产品**：车直行时 IMU 测的加速度方向应与轮速方向一致，用日常行驶数据就能**反向标定 IMU 安装角**，不用进标定间——量产车的"在线外参自标定"。
- **注意**：约束在侧滑、漂移、急转向时失效（轮胎打滑），要靠 IMU 横向加速度识别出来临时放开，否则会把真实侧向运动当噪声滤掉。

### 四、odom 系：原点为什么是 t=0 的车体系

世界原点 = **系统启动那一刻的车体系**。

**为什么不直接用"当下的车体系"**？因为车体系每帧都在动——把一个静止路灯写在车体系里，下一帧车一开坐标就变了，跟踪器每次都要重建目标，根本没法做。所以要把车体系"按下暂停键"、冻结在 t=0，这个冻结的系就是 **odom 系**（也叫 local frame / 起始点系）。

原点还有两种常见定义，差一个 t=0 时的航向角：

| 定义 | x 轴朝向 | 特点 |
| :--- | :--- | :--- |
| **A. t=0 的车体系** | 车头 | 起始 T=I，数值直觉好；和 GNSS/地图对不齐 |
| **B. 局部 ENU** | 正东 | 可直接对 GNSS/HD 地图；起始带一个 `R_z(θ₀)` |

`T_odom←body(t) = R_z(θ₀) · T_ENU←body(t)`

工程上通常**两个都留**：内部跟踪用 A（连续、不跳），对外发布时转成 B。原点定在后轴中心、质心、IMU 上也都是约定，**全局一致就没错**。

#### 必须分清：漂的是位姿，不是原点

- **原点不动**——它是定义出来的常数，写在代码里。
- **漂的是 `T_{odom←b}(t)`**，也就是"你以为自己在哪"。跑十公里后你以为回到原点，实际偏了几米。

所以 odom 系是**自洽、连续，但不保证正确**的参考系。把它按到真实世界上，靠的就是 ③ 那个 `T_{map←odom}`。

> **odom 系保证"连续"，map 系保证"正确"，两者分工。**

### 五、检测物体到底放在哪个系

**不是"车体系"，是"冻结在 t=0 的车体系"，也就是 odom 系。**

```
[相机] ─检测→ 相机系 ─┐
                      ├─ T_{b←s}(静态) → 车体系(t) ─ T_{odom←b}(t) → odom 系
[雷达] ─检测→ 雷达系 ─┘                                  ↑
                                             两个传感器共用同一条轨迹
```

这就是**跨传感器融合的全部秘密**：相机看到一辆车、雷达也看到同一辆车，都搬到 odom 系后两个点应落在同一位置（差一个传感器误差）。关联退化成"比两点距离"，不用再管视角、尺度、时间差。

**odom 系 vs map 系的分流：**

| 目标类型 | 活在哪个系 | 谁维护 | 寿命 |
| :--- | :--- | :--- | :--- |
| 动态目标（车、人、骑手） | **odom 系** | 跟踪器实时维护 | 几秒 |
| 静态目标（车道线、红绿灯、路牌） | **map 系** | HD 地图 / 长期建图 | 长期 |

- 理由：动态目标寿命短，只要**相对自车准**就行，不需绝对正确 → 放 odom 系，**避开 RTK 跳变**；静态目标必须**绝对正确**（车道在哪有国标）且跨行程复用 → 放 map 系。
- 决策时临时用 `T_{map←odom}` 把动态目标搬进 map 系判断"是否压线"，判断完就丢。

**为什么不能合并成一个系**：若每次 RTK 修正来了就把所有跟踪目标重投影一次，那些目标会瞬移几厘米到几米，IOU 关联直接崩，一堆目标被杀掉又新建，速度估计全是尖峰。典型症状：**"RTK 一收敛，目标列表就闪一下"**。

### 六、工程上真正会踩的坑（清单）

1. **方向约定**：`T_wc` 还是 `T_cw`？SLAM 库和融合代码很可能相反。看到 (R, t) 先确认方向——第一号 bug 来源。
2. **时间戳，不是"帧"**：检测管线（曝光 → 推理 → 发布）有 50–200 ms 延迟。必须维护 **100 Hz、2–5 秒的位姿环形缓冲**，收到 t 时刻的检测就去查 t 时刻的位姿。忘了做的典型症状：**车转弯时所有物体集体往一边滑**。
3. **硬件时钟同步**：IMU/轮速/相机/雷达必须打在同一个时钟上（PTP/gPTP 或硬件触发）。没对齐的话上面所有推导都白搭——**比标定更容易出事**。
4. **为什么不能直接用 GNSS 输出**：三个理由任一都够——频率（5 Hz 插不出 100 ms 内的运动，60 km/h 时 100 ms 走 1.67 m，插出来是折线，点云被甩飞）；跳变（RTK fix 在浮点解/固定解间切换有厘米到分米级阶跃，对跟踪器是灾难）；失锁（隧道、峡谷、地库直接没了）。**GNSS 的角色是修正项，不是主源。**
5. **非完整性约束失效**：侧滑、漂移、雨天打滑时 `v_y=0` 不成立。硬套约束会把真实侧向运动抹掉，表现为"雨天横向定位不准"。
6. **标称固定 ≠ 永远准**：振动、温漂、轻微碰撞都会让 `T_{b←l}` 漂，跑几百公里就该考虑重标。理论上外参固定，工程上有"多久重标一次"的问题。
7. **IMU 当 body 的代价**：把车体系定在 IMU 上省掉了 `T_{b←imu}`，但反过来 IMU 自身的**安装角**要在标定阶段一并解出来，别漏。
8. **静止物体的速度必须在 odom 系里差分**：速度 = 位置对时间求导，这个求导**只能在 odom 系做**。在车体系里差分，静止物体看起来正以车速向后跑，还得补 `v_ego` 和 `ω×r` 两项，很容易漏掉角速度那部分。
9. **单目视觉里程计的尺度**：单目 VO 有尺度不确定性，单独用它提供的 ΔT 和 IMU/轮速的米制尺度对不上，必须**联合估计**。
10. **长距离用 float32 会丢精度**：地心/UTM 坐标数值太大，float32 有效位数在米级就丢光了。这就是为什么内部必须用局部 odom 系（原点在车附近、数值小），只在对外接口才转经纬度。

### 七、一句话总纲

> ① **传感器→车体**靠标定，一次性、永不改变——因为它是**相对量**，两个传感器一起动时自动抵消；
> ② **车体→世界**靠 IMU 测旋转 + 轮速测平移，用非完整性约束降维，输出 100 Hz 连续轨迹，GNSS/激光低频修正漂移；
> ③ **odom 系 = t=0 冻结的车体系**，它保证连续但会漂；map 系保证正确但会跳，两者用一个 `T_{map←odom}` 连接；
> ④ **所有检测汇聚到 odom 系**，跨传感器融合退化成比距离，动态目标留在这个系里避开 RTK 跳变，决策时再临时搬进 map 系对着车道判断。
>
> 真正要小心的从来不是这套公式，而是**方向约定、时间戳、以及别把 ①②③ 三种变换当成同一种东西**。

## 单目 RGB 的深度缺失：为什么像素不能直接变到车体系（追问补充）(2026.09)

> 来源：追问"单目 RGB 只有 (u,v) 没有深度，是不是就没法通过 `T_cb` 变到车体系"。一句话：**对，链条断在第一步——不是外参有问题，而是单张 RGB 像素反推不出相机系 3D 点；实际系统里深度要么由 LiDAR/双目提供，要么由地面假设 + IPM 提供，要么由单目深度估计 / BEV 网络预测，图像本身只提供语义。**

### 一、像素 → 相机坐标，缺的到底是什么

相机成像模型：

```
[u]         [X_c]
[v] = (1/Z_c)·K·[Y_c]
[1]         [Z_c]
```

反推相机坐标：

```
[X_c]            [u]
[Y_c] = Z_c · K⁻¹·[v]
[Z_c]            [1]
```

**关键：`Z_c` 未知。** 没有 `Z_c`，你只能得到一条从光心出发的**射线**，无法确定射线上的哪个点。

> 所以"单目 RGB 像素没有深度就没有相机坐标"这个判断是对的——**`T_cb` 本身没问题，问题在于它作用的对象（相机系 3D 点）根本还没求出来。**

### 二、实际系统怎么把图像信息落到车体系（四种情况）

#### 情况 A：有深度传感器（LiDAR / 深度相机 / 双目）——最直接

1. LiDAR 给出点在**雷达系**下的 3D 坐标 `(X_l, Y_l, Z_l)`；
2. 通过外参 `T_lb` 变到车体系 B；
3. 通过 `T_cb` 的逆，把 3D 点**投影**到相机像素 `(u, v)`；
4. 于是每个（投影到的）像素就对应一个已知深度的 3D 点。

反过来，图像上检测到一个像素想找它的 3D 位置：**先把 LiDAR 点云投影到图像，找到与该像素对应的 LiDAR 点**，那个点自带 3D 坐标。

> **LiDAR 提供深度，图像提供语义，两者通过外参对齐**——这是融合里最基本的分工。

#### 情况 B：纯视觉 + 几何假设（地面平面）

若已知：相机高度、相机俯仰角、地面是平面，则对**地面上的点**可用"地面平面约束 + 像素射线求交"解出 `Z_c`，得到相机坐标再变到车体系。

- 这就是车道线检测、地面箭头识别、BEV 感知常用的思路：假设目标在地面上，用 **IPM（逆透视变换）** 把图像映射到地面 BEV。
- **局限**：对非地面物体（车辆、行人、空中目标）假设不成立，**单目无法直接得到准确 3D 位置**。

#### 情况 C：单目深度估计 / 神经网络预测深度

用单目深度估计网络预测每像素的 `Z_c`，再代入上式得相机坐标，最后 `T_cb` 变到车体系。

- **缺点**：单目深度是**相对/尺度不确定**的，精度有限，通常用于辅助，不用于高精度定位。

#### 情况 D：纯 2D 检测，根本不需要 3D

任务只是"图像上有没有车"时，检测框就是像素坐标，**不需要转到车体系**。只有需要 BEV 位置、跟踪、规划控制时，才需要 3D 坐标。

### 三、那条链条对单目 RGB 意味着什么

```
相机系 → 车体系 B → odom → map
```

链条成立的前提是：**你已有一个相机系下的 3D 点 `(X_c, Y_c, Z_c)`。**

| 3D 点来源 | 链条是否走得通 |
| :--- | :--- |
| LiDAR 投影 | ✅ 深度由 LiDAR 提供 |
| 地面假设 + IPM | ✅ 深度由地面约束提供 |
| 只有单张 RGB 像素 | ❌ **断在第一步**——连相机系 3D 点都得不到 |

- **`T_cb` 本身没问题**，它描述相机系与车体系的刚体变换；
- **问题在于单目 RGB 缺少深度**，无法从像素得到相机系 3D 点；
- **解决深度来源，链条才能走通。**

### 四、多传感器融合的典型流程

```
1. LiDAR 点云 → 通过 T_lb 到车体系 B
2. 同时通过 T_cb 投影到图像，和图像检测结果关联
3. 关联上的检测目标，继承 LiDAR 点的 3D 坐标
4. 这个 3D 坐标再通过 T_{odom←B}(t) 变到 odom
5. 再通过 T_{map←odom} 变到 map
```

图像在这里提供**语义信息**（是什么、检测框），3D 位置由 LiDAR 提供，两者通过外参对齐——**而不是从像素直接算 3D**。

### 五、纯视觉 BEV（BEVFormer、LSS）怎么绕开这个限制

这类方法用神经网络**隐式或显式地预测深度分布**：

| 方法 | 做法 |
| :--- | :--- |
| **LSS** | 对每个像素预测一组**深度概率**，把图像特征"抬升"到 3D 空间，再投影到 BEV |
| **BEVFormer** | 用 Transformer 在 BEV query 和图像特征间做**交叉注意力**，隐式学习 3D 对应关系 |

它们不显式输出每个像素的深度，但网络内部学到了"像素 → 3D"的映射，输出的 BEV 特征可直接放在车体系或 odom 系下。

> 纯视觉也能做 BEV，但靠的是**学习出来的深度/对应关系**，不是几何上从单像素直接算出来的。

### 六、一句核心总结

> **单目 RGB 只有像素坐标、没有深度，确实无法直接得到相机系 3D 点，也就无法直接通过 `T_cb` 变到车体系 B。** 实际系统里 3D 位置要么由 LiDAR / 深度相机提供，要么由地面平面假设 + IPM 提供，要么由单目深度估计 / BEV 网络预测；**图像本身提供语义，3D 几何由其他来源或网络补上，外参 `T_cb` 只负责把两个坐标系对齐。**

## 纯视觉测距的六条路线：不一定要双目（追问补充二）(2026.09)

> 来源：追问"没有深度是不是就得用双目测距、是不是靠这个触发 ABS"。一句话：**双目只是纯视觉测距的一条路线，单目也能测距（地面假设 / 已知尺寸 / 深度估计 / 时序三角化 / 网络回归）；量产纯视觉常用"多摄像头 + 时序 + 神经网络"的组合，距离是学出来的；而 ABS 靠轮速传感器，视觉测距服务的是 AEB/ACC。**

### 一、双目：最直接的几何测距

两个镜头、基线 `b` 已知，同一物体在左右图的像素横坐标差为**视差** `d`：

```
Z = (f · b) / d
```

- 视差越大物体越近，越小越远。

| 优点 | 缺点 |
| :--- | :--- |
| 纯几何、不需学习、物理可解释；纹理丰富、光照良好时精度不错 | 需精确标定 + 立体匹配；弱纹理/重复纹理/光照差/远距离时匹配困难；**远距离视差极小 → Z 对 d 误差极其敏感**（Z 与 d 成反比）；基线有限，测距范围受限 |

> 双目是经典路线，但**不是唯一路线**。

### 二、单目 + 几何假设

#### （1）地面平面假设 + IPM

若目标在地面上（前车、车道线），且已知相机高度 `h`、俯仰角、地面为平面，则**像素射线与地面平面求交**解出深度 `Z`，再变到车体系——这就是**逆透视变换（IPM）**。

- ✅ 不需要双目、不需要深度学习、几何清晰；
- ❌ 只对地面上的点有效，对空中/悬空/坡道/颠簸场景不成立。

#### （2）已知物体尺寸

假设前车真实宽度 `W`（比如所有车宽约 1.8 m），图像上量出像素宽度 `w`：

```
Z ≈ (f · W) / w
```

- ✅ 单目即可、简单；
- ❌ 尺寸假设不一定成立（卡车、摩托、不同车型），误差大，只能粗估。

### 三、单目 + 深度学习

#### （1）单目深度估计

网络对每像素预测 `Z`，再 `[X_c,Y_c,Z_c]ᵀ = Z_c·K⁻¹[u,v,1]ᵀ`，经外参变到车体系。

**问题：尺度不确定**——单张图无法区分"很近的小物体"和"很远的大物体"，网络只能学相对深度或依赖数据先验的绝对深度，泛化性和精度有限。

#### （2）目标检测 + 距离回归

网络检测到前车，**直接回归它的距离**（训练时用 LiDAR/双目/真值距离监督）。很多量产纯视觉方案是这条路线：

- 输出 = 检测框 + 类别 + **距离 + 速度**；
- 距离由网络回归，**不靠几何公式**；
- ✅ 单目即可、端到端、能处理非地面目标；
- ❌ 本质是学出来的先验，遇到训练分布外场景（罕见车型、极端光照、遮挡）可能失效；可解释性差；需大量标注。

### 四、单目 + 时序：运动恢复结构（SfM）

相机在运动时，连续帧之间可提供视差：

- 上一帧到当前帧相机移动了已知距离（由轮速/IMU 提供）；
- 同一物体在两帧中的像素位移，提供类似双目的视差；
- 用**三角化/多视图几何**恢复深度。

也叫运动恢复结构（SfM）或"视觉里程计 + 三角化"。

- ✅ 单目即可、利用时序；
- ❌ 需足够相机运动（**静止或低速时退化**）；需精确位姿估计；对动态物体、弱纹理、快速运动鲁棒性差；计算复杂。

### 五、量产纯视觉实际怎么做

特斯拉这类量产"纯视觉"方案通常是**多摄像头 + 时序 + 神经网络**的组合，而不是单纯依赖某一种几何方法：

- 多摄像头（前视、侧视、后视）提供不同视角；
- 时序信息提供运动视差；
- 神经网络学习深度/距离/速度；
- 用大量车队数据做监督训练；
- 输出 **BEV 下的 3D 目标、距离、速度**，而不是从单个像素用公式算出来的。

> 既不是传统双目，也不是单目几何公式，而是**数据驱动的多视角 + 时序 3D 感知**。

### 六、澄清：ABS 不靠视觉，"能测前车距离就触发 ABS"这个说法不准确

ABS（制动防抱死）主要靠**轮速传感器**判断车轮是否抱死，**不需要视觉测距**。视觉测距服务的是：

| 功能 | 依赖 |
| :--- | :--- |
| AEB（自动紧急制动） | 前车距离 + 相对速度 |
| ACC（自适应巡航） | 前车距离 + 相对速度 |
| 前碰撞预警 | 前车距离 + 相对速度 |

正确的分工是：**视觉测距 → 触发制动请求 → ABS 再根据轮速决定是否介入防抱死。**

### 七、六条路线对比

| 方法 | 需要什么 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **双目** | 两个相机 + 标定 | 纯几何、可解释 | 远距离差，纹理弱失效 |
| **单目 + 地面假设** | 相机高度/俯仰 | 简单，地面目标有效 | 只对地面点有效 |
| **单目 + 已知尺寸** | 物体尺寸假设 | 简单 | 尺寸假设不准 |
| **单目深度估计** | 网络 | 单目即可 | 尺度不确定，泛化差 |
| **单目 + 时序 SfM** | 运动 + 位姿 | 单目即可 | 静止/低速退化，复杂 |
| **多摄像头 + 网络** | 多视角 + 时序 + 数据 | 量产主流，鲁棒 | 需大量数据，可解释性差 |

### 八、一句核心总结

> **纯视觉测距不一定要双目。** 双目用视差做几何测距，单目可以用地面假设、已知尺寸、深度估计、时序三角化或神经网络回归来测距。**量产纯视觉方案通常是多摄像头 + 时序 + 神经网络的组合，距离是学出来的，不是从单个像素用公式算出来的。** 而 **ABS 本身靠轮速传感器**，视觉测距主要用于 AEB/ACC 等前向碰撞功能。

## 动态模型并行（层副本可换卡）与 KV 缓存的冲突（2026.09）

> 来源：追问"模型并行能不能替换使用——层1 的 A 跑完，层2 可以调 A 也可以调 B，输出哪张卡有空就进哪张，那 KV 缓存怎么记"。一句话：**计算可以无状态地动态路由，但 KV 缓存是有状态的，它把"请求—层—卡"三者绑在一起；动态模型并行的难点不在算力调度，而在如何低成本地维护和迁移这份状态。**

### 一、先把设想翻译成并行术语

> 设想："层1 的 A 跑完，调层2 的 A 也可以调层2 的 B，然后输出哪张层3 卡有空就进去。"

| 设想中的描述 | 对应概念 |
| :--- | :--- |
| 层2 有 A、B 两份 | 层/专家的**多副本** |
| 层1 输出可以进 A 或 B | **动态路由 / 负载均衡** |
| 层3 哪张卡有空就进 | **在线调度（scheduling）** |

**直觉是对的**：模型并行不一定非要"层1 永远在卡0、层2 永远在卡1"这种静态绑定，可以做成动态、按负载调度的。工业界已有对应实践：

| 系统/概念 | 做法 |
| :--- | :--- |
| **MoE（Mixture of Experts）** | 每个 token 路由到不同专家（层内多副本） |
| **DeepSeek / Switch Transformer** | 专家分布在多卡，token 动态分发 |
| **Orca / vLLM continuous batching** | 请求动态进出不同计算单元 |
| **Serverless 推理** | 层作为独立服务，按空闲度调度 |

### 二、核心矛盾：KV 缓存

#### 1. KV 缓存是什么

自回归生成每生成一个新 token，注意力需要用到**之前所有 token 的 K、V**；为不重复计算就存下来，这就是 KV Cache。

```
第 t 步生成时：
  当前 token 的 Q × [历史所有 K] → 注意力权重
                  [历史所有 V] → 加权求和
  历史 K、V 就是 KV Cache，不用重算
```

形状大致：`[num_layers, batch, num_heads, seq_len, head_dim]`

> **关键：KV Cache 是"按层"存的，而且和"哪个请求、哪段历史"强绑定。**

#### 2. 动态调度与 KV 缓存的冲突

假设层1 在卡0 算完，请求 R 的 KV 存在**卡0 的层1缓存**里。现在层2 要动态选卡：

- 若层2 选到**卡1 的副本 A** → 卡1 没算过 R 的层2，**没有这份 KV**，要么重算、要么从卡0 传过来；
- 若选到**卡1 的副本 B**（另一份拷贝）→ 同样没有 R 的层2 KV；
- 而**下一步生成**时层2 又可能被调度到另一张卡，那份 KV 又得跟着搬。

> **KV 缓存和"计算它的那张卡、那个模型副本"是绑定的。动态换卡 = 缓存要么跟着搬，要么重建。**

### 三、工业界的五种解法

| 方案 | 做法 | 优点 | 缺点 / 适用 |
| :--- | :--- | :--- | :--- |
| **① KV 跟着请求走（迁移）** | 请求被调度到哪张卡，就把它的 KV 一起搬过去 | 调度自由 | KV 很大（长上下文每层几 MB~几十 MB），**跨卡带宽是瓶颈**（NVLink 尚可，PCIe 很慢）；适用于 PD 分离 |
| **② 请求亲和性调度（Affinity）** | 同一请求的所有层**尽量固定在同一组卡**上，调度器记录"R 的 KV 在卡0/1/2"，后续优先调度到这几张卡；只有全忙时才迁移 | 避免 KV 迁移 | **目前 LLM serving 的主流做法**：KV 亲和性 > 纯负载均衡 |
| **③ 副本间共享 KV** | 副本 A/B 要处理同一请求 R 时**共享同一份 KV**（共享显存池或 RDMA 访问） | 省复制 | 有同步开销（DeepSpeed-Inference、部分 MoE 实现这么做） |
| **④ 无状态化，每步重算** | 不存 KV，每步重算整个序列的 K/V | 无缓存管理 | 计算量 O(n²) 爆炸，只适合极短序列或训练 |
| **⑤ 层为调度单位 + KV 按请求分片** | Prefill 全部层在卡组上算完生成完整 KV；Decode 时各层在各自卡上维护自己那段 KV，**请求固定绑定这条流水线**；动态调度只发生在**请求进入时** | 兼顾流水线与局部性 | 进入后不再换卡 |

**vLLM 的 PagedAttention** 是把方案①做到极致：KV 按 block 管理，可以像操作系统分页一样在卡间搬运、共享。

### 四、核心答案

1. **KV 缓存按"层 + 请求 + 历史 token"存**，天然绑定在"算过这个请求这一层"的那张卡上。
2. **若允许层2 在副本 A/B 间动态切换，就必须解决**：副本 B 没有请求 R 的层2 KV → 要么**迁移**、要么**重算**、要么**共享**；下一步再切到别的卡，KV 又要动。
3. **真实系统的做法**：
   - **调度以请求为单位，而不是以层为单位**——请求一旦进入某条并行流水线就**固定绑定**，KV 留在原地，不随层乱跳；
   - 动态负载均衡只发生在**请求级别**（新请求选空闲流水线），而不是**层级别**（层2 随机选卡）；
   - 若一定要层级动态，就用 **PagedAttention 式 KV 分页 + 迁移**，代价是通信。
4. **换句话说**："层2 的 A 或 B 随便调"在**计算上**可行，但**状态（KV）**让这件事变贵——因为 KV 不是无状态的，它记得"我之前在哪张卡上算过"。工程上通常**牺牲一点调度自由度，换取 KV 的局部性（locality）**。

### 五、一句核心总结

> **计算可以无状态地动态路由，但 KV 缓存是有状态的，它把"请求—层—卡"三者绑在一起。动态模型并行的难点不在算力调度，而在如何低成本地维护和迁移这份状态。主流方案是"请求级亲和调度 + KV 分页迁移"，而不是层级的随机换卡。**

**可继续展开的方向**：PagedAttention 怎么管理 KV、MoE 怎么做专家路由、PD 分离怎么传 KV。
